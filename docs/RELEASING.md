# Releasing AgentArmor

Releases are cut by pushing a `v*` tag. The [release workflow](../.github/workflows/release.yml)
then builds the Windows installer, creates the GitHub release with assets, and
publishes the wheel to PyPI.

## One-time setup: PyPI publishing (API token)

The `pypi` job publishes with an **API token**. Add it once:

1. On [pypi.org](https://pypi.org): **Account settings → API tokens → Add API token**.
   Scope it to the `agentarmor` project (create the project first by uploading a
   wheel manually if it does not exist yet).
2. Copy the token (starts with `pypi-...`).
3. In the GitHub repo: **Settings → Secrets and variables → Actions → New repository
   secret**. Name it exactly **`PYPI_API_TOKEN`** and paste the token.

Until this secret is set the `pypi` job fails, but it is `continue-on-error`, so
the Windows installer release still succeeds. After adding the secret you can
re-run the failed `pypi` job on the most recent release run to publish that
version.

## Cutting a release

### Version strings

`agentarmor/__init__.py` holds `__version__` and is the **single source of truth**.
`pyproject.toml` reads it via `[tool.hatch.version]`, so those two can no longer
drift. They did before: this checklist used to omit `__init__.py`, and 1.4.1 through
1.4.3 all shipped reporting 1.4.0 in `/health`, in the desktop status pill and
stamped into every HTML and PDF report.

Bump `__version__`, then these copies, which exist because npm and Tauri need the
value literally:

- `gui/package.json` (`version`)
- `gui/src-tauri/tauri.conf.json` (`version`) — the installer filenames come from this
- `gui/src-tauri/Cargo.toml` (`version`), then run `cargo check` and commit the
  updated `gui/src-tauri/Cargo.lock`
- `README.md` — the version badge, the "Latest release" line (the version appears
  **twice** on it: link text and tag URL), and the installer filename
- `action/action.yml` — the `version` input default. The README's own Action example
  does not pass `version`, so this default is what documented usage installs.
- `CHANGELOG.md` — a new dated section. **Required:** the release workflow builds the
  GitHub release body from it and fails if the section for the tag is missing.

`tests/test_version_sync.py` asserts every one of these agrees with
`agentarmor.__version__`. `pytest` is the required check, so drift fails CI instead
of shipping.

### Release notes

The GitHub release body is generated by `scripts/changelog_section.py` from the
changelog section for the tag being built. There is no file to maintain, and no way
to publish stale notes: a missing section fails the release.

This replaced `docs/RELEASE_BODY.md`, which was wired in unconditionally and shipped
v1.4.0 notes as the body of v1.4.1, v1.4.2 and v1.4.3 — telling users to download
installer filenames that did not exist in those releases.

### Before tagging

- `pytest -q` green.
- `cd gui && npm test` green, and `npm run build` succeeds.
- `python -c "import agentarmor; print(agentarmor.__version__)"` matches the tag.
- `python -m build --wheel` produces a wheel whose filename carries the new version.
- `python scripts/changelog_section.py vX.Y.Z` prints the expected notes.
- `git status` clean.

Then:

```bash
git commit -am "Release vX.Y.Z"
git push origin main
git tag -a vX.Y.Z -m "AgentArmor vX.Y.Z — ..."
git push origin vX.Y.Z
```

Pushing the tag triggers the full pipeline. No pull request is required for a
release.
